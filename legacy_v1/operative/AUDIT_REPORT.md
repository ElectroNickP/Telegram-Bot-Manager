# Отчет об аудите проекта Telegram-Bot-Manager
**Дата:** 22.11.2025
**Статус:** Завершен

## 1. Executive Summary (Резюме)
Проект находится в состоянии **незавершенной миграции/рефакторинга**. Существует серьезный разрыв между "старой" кодовой базой в папке `src/` (которая работает в продакшене) и "новой" архитектурой в корневых папках `core/`, `adapters/`, `apps/`. 

Обнаружена **КРИТИЧЕСКАЯ УЯЗВИМОСТЬ**: файл конфигурации с боевыми токенами находится в репозитории.

Технический долг высок (2600+ ошибок линтера), инфраструктура Docker предназначена скорее для тестирования установки, чем для промышленной эксплуатации в контейнерах.

---

## 2. Критические проблемы (Critical Issues)

### 🚨 2.1. Утечка секретов (Security)
В файле `bot_configs.json` обнаружены **захардкоженные боевые токены**:
- `telegram_token`: `7684104886:AAHC_...`
- `openai_api_key`: `sk-proj-...`
- `assistant_id`: `asst_...`

**Риск:** Полная компрометация бота и OpenAI аккаунта (финансовые потери).
**Рекомендация:** Немедленно отозвать (revoke) токены, удалить файл из истории git (git filter-repo) и добавить его в `.gitignore`. Использовать `.env` или переменные окружения.

### 🏗️ 2.2. Архитектурный "Split Brain"
В проекте существуют две параллельные структуры:
1.  `src/` — Легаси код, монолитная структура. Используется скриптом `start-prod.py`.
2.  `core/`, `adapters/`, `apps/` — Новая Clean Architecture. Используется частично в тестах и, видимо, планировалась как целевая.

Скрипт `start-prod.py` принудительно делает `os.chdir("src")`, игнорируя новую архитектуру. Тесты (`tests/conftest.py`) также добавляют `src` в `sys.path`, но некоторые тесты пытаются импортировать `core`.

**Риск:** Путаница при разработке, сложность поддержки, баги из-за рассинхронизации логики.

## 3. Качество кода (Code Quality)

- **Линтинг (Ruff):** Найдены **2694 ошибки**.
    - Основные: устаревшие аннотации типов (`UP006`), проблемы с форматированием (`W293`), неиспользуемые импорты.
    - Конфигурация `ruff` в `pyproject.toml` использует устаревшие секции.
- **Типизация:** Отсутствует строгая проверка типов во многих модулях.
- **Логирование:** Логи пишутся в файлы в корне проекта (`bot.log`, `server.log`), что плохо для Docker/Cloud native подходов (нужен stdout/stderr).

---

## 4. Инфраструктура (Infrastructure)

### Docker
Файлы `Dockerfile` и `Dockerfile.fixed` не являются Docker-образами приложения в классическом понимании. Они представляют собой образы "чистой Ubuntu" для тестирования скрипта установки (`start.py`).
- Нет `ENTRYPOINT` на запуск приложения.
- Используется `systemd` подход внутри контейнера (установка venv, pip install), что не идиоматично для Docker.

### Деплой
Скрипт `start-prod.py` полагается на создание `venv` на хост-машине. Это рабочий подход для VPS, но устаревший для современного CI/CD.

## 5. Хранение данных
Используются JSON-файлы (`bot_configs.json`, `adapters/storage/json_adapter.py`).
**Риск:** Потеря данных при конкурентной записи, сложность миграции схем, отсутствие транзакций.

## 6. Рекомендации (Roadmap)

### Фаза 1: Безопасность (Срочно)
1.  Отозвать текущие API ключи.
2.  Добавить `bot_configs.json` в `.gitignore`.
3.  Перевести загрузку конфигов на `.env` или Environment Variables (как сделано в `config.yaml`).

### Фаза 2: Стабилизация архитектуры
1.  Принять решение: либо полностью переключиться на `core/` (завершить рефакторинг), либо удалить `core/` и навести порядок в `src/`. Рекомендуется **завершить переход на Clean Architecture**.
2.  Исправить `start-prod.py` (или создать новый `entrypoint`), чтобы он запускал приложение из корня, используя `core`.

### Фаза 3: Инфраструктура
1.  Написать настоящий `Dockerfile` (multi-stage build, без venv, запуск через gunicorn напрямую).
2.  Настроить `docker-compose` для локальной разработки (app + db + redis).

### Фаза 4: Качество кода
1.  Обновить конфиг `ruff`.
2.  Исправить автоматические ошибки (`ruff check --fix`).
3.  Настроить `pre-commit` хуки.
